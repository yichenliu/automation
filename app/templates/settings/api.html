A key acts like a person with that role: it sees only what the role may see, and the tables' rules and locks apply. Every change it makes is in the records' history.

{{ icon('code') }}

Using it

curl {{ config.BASE_URL }}/api/v1/tables -H "Authorization: Bearer YOUR_KEY"
curl "{{ config.BASE_URL }}/api/v1/tables/TABLE/records?status=Open&sort=-created_at&limit=50" -H "Authorization: Bearer YOUR_KEY"
curl -X POST {{ config.BASE_URL }}/api/v1/tables/TABLE/records -H "Authorization: Bearer YOUR_KEY" \
     -H "Content-Type: application/json" -d '{"name": "Acme", "status": "Open"}'
curl -X PATCH {{ config.BASE_URL }}/api/v1/tables/TABLE/records/ID -H "Authorization: Bearer YOUR_KEY" \
     -H "If-Match: VERSION" -H "Content-Type: application/json" -d '{"status": "Done"}'

Line items go with their record: {"client": "Acme", "lines": {"invoice_lines": [{"description": "Labour", "quantity": 2}]}}. Linked records can be given by name or id. Send If-Match with the version you read and a change made by someone else in the meantime is refused (409) instead of overwritten.

Use it from an AI assistant

Claude, ChatGPT, Cursor, Copilot and other assistants can find, read, add and change records here, with a key's role and the app's rules, as a person would. Give the assistant this address and a key:

{{ base }}/api/v1/mcp

Claude Code: claude mcp add --transport http {{ (ws.blueprint.get('name') or ws.name)|lower|replace(' ', '-') }} {{ base }}/api/v1/mcp --header "Authorization: Bearer keel_…"
Cursor, VS Code and others: add an MCP server with that address (streamable HTTP) and the header Authorization: Bearer keel_….
A viewer key only lets it read.

For code and reporting tools, the API with this app's own lists and fields as types: {{ base }}/api/v1/openapi.json (send the key the same way).
